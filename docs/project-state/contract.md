## RFN-001 local four-channel refund contract

Owner requested Stripe/Creem refunds, local integration/regression only, with real-platform testing after deployment. CAP-007 expands compatibly; existing PayPal/Waffo rules, flags and accepted records remain unchanged.

- Migration 0010 only expands payment_refunds provider constraint. All four providers use the same admin authorization, immutable request UUID, user/order lock, original package hold/reclaim/release and audited loss-waiver service. No database reset, key change or second-site source upgrade.
- Backend refund creation stays sandbox/test only. New-channel disabled/missing configuration fails before reservation. Stripe supports cumulative partial/full refunds; its original invoice receipt resolves exactly one paid PaymentIntent. Creem POST /v1/refunds accepts only transaction_id, so partial requests are rejected before holding credits and one transaction-level full-refund identity is shared by query and callback. The platform ref_ ID, when supplied by a signed notification, is retained in ticket_id; confirmed failed attempts have separate identities so a later explicitly requested retry cannot strand its hold.
- Standard USD cash amount must match the stored original order. Tax-inclusive, discounted, multiple-payment or ambiguous associations require manual reconciliation; no speculative cash request. Refunds affect the original paid-period package and do not cancel subscriptions or affect other periods. Cancellation/resume remain explicit, separate operations.
- Unconsumed, unexpired and unfrozen source credits are reserved atomically before cash submission. Consumed/expired/frozen packages record BLOCKED without a cash call. Confirmed success turns the source reservation into reclaimed credits once; confirmed failure releases once without extending expiry. Unknown results retain reservations and permit query-only recovery, never blind POST retry.
- External successful refunds reclaim original-source remainder only. Consumed/frozen shortfall gates new tasks, while pre-existing tasks continue; failures repay the debt from the original released source within the same transaction, successes retain a review shortfall. No other package is debited; loss waiver remains attributed/idempotent.
- Signed raw Stripe refund.created/updated/failed (and charge.refund.updated) events use authenticated refund queries. Creem refund.created uses HMAC verification then authenticated original-transaction verification. Different event IDs, concurrent delivery and query/callback races cannot double-debit. A reused event ID with changed fingerprint is refused. Financial failures roll back projections/package/ledger and verified events can recover.
- Gates: test-four-channel-refunds.ts (13 groups), test-refund-browser.mjs (real local auth/route/UI guards; server providers disabled), all eight retained suites, billing/browser/production and independent-site checks, typecheck/build and clean fixture snapshot. Successful provider operations are isolated adapter fixtures, not actual receipts. See parent FOUR-CHANNEL-REFUND-GUIDE.md and refunds-results.json.
