## AUD-004 local billing contract

Owner decision DEC-AUD004-LOCAL-20261101: “先完成本地接入与回归，正式部署后再做 Creem 真实测试”. Local QA is this task's completion gate; real Stripe/Creem acceptance and live activation remain separate. The Creem account currently has no completed store, products or keys; no Stripe test account is available.

- CAP-010 uses the same order/event/fulfillment/credit boundaries for all four configured providers. Each checkout freezes SKU, price, credits, environment/account and external product mapping. Persistent request IDs and leases own retries; browser redirects never mint.
- Subscription state lives in billing_subscriptions; every paid period is linked through billing_cycles to a normal paid order/fulfillment. User locks, unique receipts and exact period uniqueness serialize money. Another receipt for the same cycle, overlapping periods, wrong scope/price/currency/user or ambiguous legacy records do not mint. Database faults roll back the cycle/package/ledger/order together; verified events remain recoverable.
- Active/trial/checkout/return signals alone do not issue subscription credits. Only a verified, eligible paid invoice/transaction grants once. Scheduled cancellation preserves paid coverage and original credits; resume changes provider state and grants nothing. Ended subscriptions require a new subscription. Paused Stripe billing is not automatically resumed by this version.
- Package expiry for subscriptions is the original paid period end, including late historical invoices. Newer confirmed state wins over stale callbacks; expired/canceled state cannot receive an artificial grace day.
- Existing Stripe Customer and Creem subscription associations are used before metadata fallback. Exact old Creem grants for the same period are linked rather than reminted; subsequent cycles remain eligible. Current local DB had zero real subscriptions before this migration, so this is fixture-backed compatibility, not acceptance of arbitrary production history.
- Legacy Creem financial callbacks were removed from the auth plugin. Its webhook URL forwards to the same signature adapter; access/management compatibility endpoints use the common projection. Old checkout calls without a durable request ID are refused and point to the unified purchase page. Stripe authentication remains separate from billing.
- PayPal/Waffo flags, models, prices, paid/refunded records and refund rules remain preserved. RFN-001 later adds local Stripe/Creem refund adapters; their real refund/reversal acceptance is not claimed and both channels remain disabled.
- Prices are the existing USD 5/100 and USD 15/350 one-time catalog; recurring amounts/credits retain pricing-user.ts. Per-channel external IDs use environment mappings and per-product UI eligibility. No coupons, seats, upgrade proration or historical price migration is silently treated as a full standard cycle.
- Migration 0009 is additive apart from expanding the provider constraint. It adds order kind/product snapshot and scoped subscription/period tables, retaining existing rows. The main Stripe SDK/API pin is 23.1.0 / 2026-10-28.endive; other accepted dependencies remain fixed.
- Gates: seven retained integration/API suites (including billing), browser/API auth and submit contract, production isolation, typecheck/build, security threshold and second-instance isolation. Provider fixtures use fake keys and mocked provider responses; no new real-provider calls. Configuration and deferred account gates: parent AUD-004-BILLING-GUIDE.md.

## RFN-001 local four-channel refund contract

Owner requested Stripe/Creem refunds, local integration/regression only, with real-platform testing after deployment. CAP-007 expands compatibly; existing PayPal/Waffo rules, flags and accepted records remain unchanged.

- Migration 0010 only expands payment_refunds provider constraint. All four providers use the same admin authorization, immutable request UUID, user/order lock, original package hold/reclaim/release and audited loss-waiver service. No database reset, key change or second-site source upgrade.
- Backend refund creation stays sandbox/test only. New-channel disabled/missing configuration fails before reservation. Stripe supports cumulative partial/full refunds; its original invoice receipt resolves exactly one paid PaymentIntent. Creem POST /v1/refunds accepts only transaction_id, so partial requests are rejected before holding credits and one transaction-level full-refund identity is shared by query and callback. The platform ref_ ID, when supplied by a signed notification, is retained in ticket_id; confirmed failed attempts have separate identities so a later explicitly requested retry cannot strand its hold.
- Standard USD cash amount must match the stored original order. Tax-inclusive, discounted, multiple-payment or ambiguous associations require manual reconciliation; no speculative cash request. Refunds affect the original paid-period package and do not cancel subscriptions or affect other periods. Cancellation/resume remain explicit, separate operations.
- Unconsumed, unexpired and unfrozen source credits are reserved atomically before cash submission. Consumed/expired/frozen packages record BLOCKED without a cash call. Confirmed success turns the source reservation into reclaimed credits once; confirmed failure releases once without extending expiry. Unknown results retain reservations and permit query-only recovery, never blind POST retry.
- External successful refunds reclaim original-source remainder only. Consumed/frozen shortfall gates new tasks, while pre-existing tasks continue; failures repay the debt from the original released source within the same transaction, successes retain a review shortfall. No other package is debited; loss waiver remains attributed/idempotent.
- Signed raw Stripe refund.created/updated/failed (and charge.refund.updated) events use authenticated refund queries. Creem refund.created uses HMAC verification then authenticated original-transaction verification. Different event IDs, concurrent delivery and query/callback races cannot double-debit. A reused event ID with changed fingerprint is refused. Financial failures roll back projections/package/ledger and verified events can recover.
- Gates: test-four-channel-refunds.ts (13 groups), test-refund-browser.mjs (real local auth/route/UI guards; server providers disabled), all eight retained suites, billing/browser/production and independent-site checks, typecheck/build and clean fixture snapshot. Successful provider operations are isolated adapter fixtures, not actual receipts. See parent FOUR-CHANNEL-REFUND-GUIDE.md and refunds-results.json.

## AUD-005 local payment operations contract

- CAP-011 owns privileged exception views and immutable, reasoned operation intents. Page/API authorization and same-origin JSON guards apply; the service rechecks current administrator state when reserving and executing. No browser-provided cash/credit facts or amount override is accepted.
- Migration 0011 adds payment_operations and event attempt/error/review metadata without resetting financial data. Actor, action, target, reason and UUID fingerprint are committed before side effects. Leases survive restart; same-ID requests return the existing intent and changed content conflicts. Independent operations still use existing receipt/cycle/refund uniqueness. Financial completion followed by audit-finalization failure recovers without another grant/debit.
- Replay loads scoped normalized records saved by trusted webhook/query services, validates outer/inner identity, and applies existing fulfillment/subscription/refund logic. Processed one-time receipts missing their fulfillment may be reconciled through immutable snapshots and unique constraints, never by rewriting existing packages. Missing/unsupported facts enter review. Subscription active/checkout alone is not a paid-period receipt.
- Compensation first checks for an existing receipt, then saved paid facts, then authenticated read-only provider lookup where supported. PayPal lookup explicitly disables capture; existing normal purchase capture behavior is unchanged. Stripe/Creem read queries reuse the accepted adapters. Waffo completed/priceSnapshot is not proof: without signed actual-payment facts it stays NEEDS_REVIEW, pending official resend/actual API validation. No checkout, capture, model call or new cash-refund request is issued by this console.
- Refund recovery delegates to query-only recheck or replay of verified refund facts. Original source/expiry/consumed/frozen/debt rules and refund uniqueness remain enforced. Dispute/reversal/unrecognized verified events are visible for review and reasoned ACKNOWLEDGED audit; this is not financial dispute resolution or automatic balance reversal.
- Queries cover orders/users/external receipts/events/refunds/operation attribution with bounded parameters and pagination. Internal hashes/leases/raw provider secrets are not projected. Provider unknown outcomes/errors leave review records; new authenticated intents may recheck after evidence/configuration is corrected, without overwriting history.
- Gates: 12 operation groups, three real local browser/API groups including committed-but-lost response and reload/same-ID retry, all nine retained suites, six second-site isolation groups, typecheck/build and production-private routes. No new real-provider calls. Source/usage and account-backed boundaries: parent AUD-005-PAYMENT-OPERATIONS-GUIDE.md, aud-005-results.json.

## AUD-006 private storage, data recovery and readiness contract

- CAP-012 adds local/S3 per-record routing to task assets and private uploads (migrations 0012/0013), without rewriting legacy local files or financial data. Current main uses a newly provisioned, private Cloudflare R2 test bucket and bucket-only object read/write credentials. No public r2.dev/custom domain is enabled. Second-site source/configuration remains at its independent AUD-003 version.
- Site namespace and persisted endpoint/bucket/region/namespace scope guard private reads; authenticated owner or verified administrator proxy controls remain. Video Range/HEAD/download and legacy local streams are tested. Video retry reuses matching immutable objects; SHA256 readback prevents silently completing bad storage. Image uploads reserve quota under user lock, validate MIME signatures/size and publish only after persistence; publicUrl is a compatibility field for the authenticated proxy, not a public object URL. Unverified legacy image-to-model handoff is explicitly outside accepted tool behavior.
- Local backups require stopped Web and no fresh running Workers, encrypt pg_dump and registered files with AES-256-GCM directly into ciphertext, authenticate the manifest, and compare full table fingerprints before/after. Independent 32-byte backup keys remain outside bundles. Restore only creates a new same-site prefixed database, verifies row/file hashes, maps private files to a new portable local root, preserves financial identity and never starts Workers or promotes a database. Wrong keys, manifest edits, corrupt payloads and existing/main targets fail. Remote production backup/PITR/failover and automatic offsite retention are not claimed.
- Each Worker owns a random process instance with 5-second heartbeat, 30-second freshness and bounded loop-progress age (text/payments 180 seconds, video 300 seconds). Required Workers follow enabled tools; payments always required. Existing queue/credit/payment behavior is unchanged. Public /api/ready returns 200/503 with bounded checks; /api/health remains liveness only. Admin-only runtime page/API displays heartbeats. No automatic process supervisor or external alert delivery is added.
- Maintenance defaults to dry-run, cleans only verified old temporary download paths and transactionally abandoned WRITING uploads with exact original scope/key; registered result deletion, automatic backup pruning and broad orphan deletion are not implemented.
